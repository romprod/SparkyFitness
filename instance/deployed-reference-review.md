Review date: 15 November 2026. This is a read-only fidelity audit, not approval to add features or change the deployed instance.

## Reference and evidence

The deployed reference reports **v1.28.1**, source revision [`b305c4c95`](https://github.com/kavo91/peptide-pitstop/commit/b305c4c95f2118051c0e03f719d9330bfe3f9818). Its resolved runtime design is **`current`**, not the optional `pitstop` design pack. The optional prescription wizard is disabled. The latest-three bloodwork matrix is also gated to the optional `pitstop` design, so it is source-existing but not shown in this deployed `current` mode; the deployed Bloodwork page shows trends and panel history. Responsive desktop/sidebar and mobile/bottom navigation are selected by layout, not a separate navigation setting. Personal theme, timezone and data-dependent screen state have not been inspected.

All **581 source files under `src/`** in the public deployed revision were byte-compared with the earlier review revision `1caffbcfaeb4ccaccee9806a37d169e013328528`: no differences. The intervening commit changes README, landing-page material, screenshots and seed data, not application source. This verifies the applicability of prior source findings across the app; it does not prove that every screen has been rendered or exercised.

Evidence levels used below:

- **Runtime/source**: running-image revision and allowlisted nonsecret flags, compiled renderer/call props, and exact public source. No authenticated owner screen or clinical record was inspected.
- **Synthetic render**: exact source components with the original CSS and synthetic fixture providers. This establishes appearance/flow for those fixtures, not the owner's saved state.
- **Code audit**: source and current Sparky implementation compared; no claim that an authenticated deployed screen was observed.

Raw deployment metadata and synthetic screenshots stay outside Git. No password reset, credential mutation, clinical write or production change is part of this audit. Native source coverage is distinct from a distributed native binary.

## Findings and next decisions

No broad parity completion is claimed. Outstanding delivered-scope differences above are either explicitly approved adaptations or partial coverage unless a reproducible defect is separately identified. Exact-source synthetic full-page renders now cover stock/preparation, settings/device management, log forms and Bloodwork in active `current` mode. They expose the original layouts and interaction paths, but do not make Sparky pixel-identical or prove the owner’s authenticated saved state.

An isolated fresh-PostgreSQL regression reproduction confirms that deleting a medication with a prepared vial and linked calculated injection fails in the preparation-scope trigger (`P0001`) introduced with preparation records in `0537758be`, leaving the transaction intact. The legacy manual-vial control succeeds and preserves the injection with its medication/vial/preparation references cleared. This delivered-model regression is corrected by forward migration `20261115190000_fix_medication_history_cascades.sql`: genuine parent cleanup clears nullable history references while direct preparation detachment and direct used-stock deletion remain protected. An isolated phase-one snapshot (baseline plus migration/test only) passed fresh migration, reapplication, eight deletion/scope cases, three preparation cases, eight syringe cases and 367 permission cases; the previous server image also passed compatibility. These are source/test results; deployment verification is separate. Tests used synthetic records only, and temporary database/user/tunnel cleanup succeeded. No production deletion was attempted.

A lower-impact API-only invariant gap remains in attaching a preparation to a legacy vial: validation checks the existing usage count/history but can accept a nonzero incoming usage count in the same patch. The normal UI does not submit this combination; balance handling correctly becomes unknown rather than inventing exact stock. This is an own-record consistency edge, not evidence of a new source feature or a cross-owner access issue.

A concrete pre-existing web and native discrepancy requires coordinator review before a fix: a notes/site-only edit rebuilds and sends the timestamp from a minute-precision local control, whereas source `EditDoseForm.tsx` submits a timestamp only if touched and `actions/doses.ts` otherwise keeps the stored instant. Web can strip seconds and change the frozen tracking day; native recombination can additionally shift the stored instant by a whole day. Web baseline code predates these ports; native code is traced to October baseline commit `1468366d72`. Synthetic examples establish the code behavior, not an observed effect on personal records. No native binary has been distributed.

Two further pre-existing web Labs issues were reproduced with synthetic data. At the initial 390-pixel viewport, the header’s More actions button lies entirely beyond the right edge (left approximately 396, right 436), obstructing direct pointer/touch access in that view. Keyboard or horizontal-navigation access was not ruled out. The unchanged header flex layout is in `SparkyFitnessFrontend/src/pages/Labs/Labs.tsx:139–167`; the comparison insertion did not introduce it.

The existing latest-marker/history formatter prioritises `value_numeric` over `value_text`, so a supported dual-field record with a qualifier can lose that qualifier and receive an exact-number In range badge. `SparkyFitnessFrontend/src/pages/Labs/labFormat.ts:56–60` and `Labs.tsx:116–130,228–234` establish the old path; `LabComparison.tsx:35–45` preserves the qualified text in the new matrix. This is a pre-existing loss of qualified-result semantics, not an L02 regression. It does not establish that the example’s In range classification is clinically wrong. No prevalence or impact on personal records was investigated.

The actionable discrepancy count is **five**: one confirmed delivered-model regression, three pre-existing defects (one timestamp issue affecting web/native, two web Labs issues), and one lower-impact API-only invariant edge. Approved adaptations and partial source coverage in the tables are not counted as defects. No new L02 regression was confirmed.

Prioritise confirmed discrepancies in already-delivered flows before selecting another source feature. Source-verified candidates after that are preparation/BUD completion, P05 protocol-version history before I06 forecasting, and C01/C02/C06 purchase-cost foundations. These are review options, not implementation authorisation. Do not infer a spill/priming ledger, generic stock adjustment, invoice OCR, numbered syringe ruler or clinical safety rules from the reference.

## Rendered reference coverage

Exact deployed public-source compositions were rendered with original CSS, responsive navigation and synthetic providers: inventory, three-step dry preparation/review, full settings/device form, ad-hoc empty/ready logging, lifecycle editing, current-mode Bloodwork trends/history/manual panel, optional Pitstop-mode matrix, original dose correction/review, and Analytics. Current Sparky synthetic full-app checks retain all-peptide access, existing Cabinet/stock placement and all three medication amount charts. Authentication, database/decryption, routing and server actions were stubbed; no clinical records or owner browser session were used. The source route shell retained actual responsive navigation but omitted Next font loading and service-worker/heartbeat/refresh effects, so the renders establish structure and flow rather than pixel-identical live appearance. Private evidence indexes cover the full-route web visual audit and the separate Labs comparison; raw artifact paths and screenshots remain outside Git.

Concrete visible differences remain explicit: Sparky uses a single preparation dialog rather than the original three-step wizard; its original-dose correction dialog remains delivered-mg based rather than the source four-unit selector and review/impact step; its syringe manager is an owned-device dialog rather than the global-capable Settings composition. The source ad-hoc form has a sticky mobile save action; Sparky retains its existing normal save-button placement. Source premixed entry uses concentration and volume, with a three-step preparation/review flow; the delivered Sparky dialog uses mass and volume. Source correction retains four input units and a review/stock-impact step, while the delivered correction dialog remains delivered-mg based with direct save. These are partial integration boundaries, not a claim of identical appearance.
